Redimensionnement d’OPcache PHP 8.4

Procédure corrigée pour le maître PHP-FPM commun aux sites en ea-php84.

Avertissement

Cette procédure redimensionne l’OPcache partagé, augmente le nombre de clés et la mémoire des chaînes internées, puis désactive le JIT. Son application exige un redémarrage qui coupe brièvement tous les sites en PHP 8.4 et vide leur cache commun. Faites-la uniquement pendant le créneau de maintenance recommandé.

La version précédente de ce document visait le mauvais fichier. Elle a été corrigée le 2026-08-01. Le fichier à modifier est /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini, avec un accès root. L’éditeur INI de WHM ne modifie que le php.ini principal et n’a donc aucun effet sur ces réglages OPcache.

À lire avant tout

Cette intervention corrige un sous-dimensionnement réel et remplace un garde-fou disparu : un script qui purgeait l’OPcache lorsque la mémoire libre passait sous 100 Mo a été supprimé entre la mi-juin et le 26 juillet 2026. Elle bénéficie à tous les sites du serveur.

Elle ne corrige pas la lenteur de la page d’accueil de laveille.ai. Cette cause a été mesurée séparément : une requête SQL de 1 642 ms représentait 94 pour cent du temps de la page. Un index ajouté le même jour a ramené le temps mesuré de 1 745 ms à 49 ms.

Diagnostic préalable

Voir les réglages de toutes les versions PHP installées

for d in /opt/cpanel/ea-php*/root/etc; do [ -d "$d" ] || continue; printf '\n=== %s ===\n' "$d"; grep -RHE '^[[:space:]]*;?[[:space:]]*opcache\.(memory_consumption|max_accelerated_files|interned_strings_buffer|jit|jit_buffer_size|validate_timestamps|revalidate_freq)[[:space:]]*=' "$d/php.ini" "$d/php.d" 2>/dev/null || printf 'Aucun réglage trouvé\n'; done

Cette lecture seule parcourt toutes les versions ea-php installées et affiche le fichier source de chaque réglage. Elle permet de repérer immédiatement un ancien réglage posé sur une version qui ne sert plus.

Lire le bon fichier de surcharge

sed -n '1,240p' /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini

Cette commande affiche le contenu actuel du fichier qui gouverne réellement OPcache. Il est chargé après le php.ini principal et après 10-opcache.ini. Le préfixe 11- gagne. Ne modifiez jamais 10-opcache.ini : cPanel le régénère lors de ses mises à jour.

Si 11-opcache-memora.ini n’existe pas, créez-le avec ce contenu complet type :

install -m 0644 /dev/null /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini && printf '%s\n' 'opcache.memory_consumption=3584' 'opcache.max_accelerated_files=130987' 'opcache.interned_strings_buffer=640' 'opcache.revalidate_freq=2' 'opcache.save_comments=1' 'opcache.jit=disable' 'opcache.jit_buffer_size=0' > /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini

Cette commande crée le fichier avec les permissions 0644, puis y écrit les cinq valeurs cibles. Ne l’utilisez que si le fichier est absent, car la redirection remplace son contenu.

2

Appliquer les cinq valeurs

Collez ce bloc unique. Pour chaque directive, il remplace une ligne existante, même commentée par un point-virgule, ou ajoute la directive si elle est absente. Il relit ensuite le fichier. L’objectif est d’éliminer le scénario « le sed n’a rien trouvé et il ne s’est rien passé ».

( set -eu
FILE=/opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini
[ -f "$FILE" ] || { echo "Fichier absent : $FILE" >&2; exit 1; }
set_ini() {
  key=$1
  value=$2
  if grep -Eq "^[[:space:]]*;?[[:space:]]*${key//./\\.}[[:space:]]*=" "$FILE"; then
    sed -i -E "s|^[[:space:]]*;?[[:space:]]*${key//./\\.}[[:space:]]*=.*|${key}=${value}|" "$FILE"
  else
    printf '%s=%s\n' "$key" "$value" >> "$FILE"
  fi
}
set_ini opcache.memory_consumption 3584
set_ini opcache.max_accelerated_files 130987
set_ini opcache.interned_strings_buffer 640
set_ini opcache.jit disable
set_ini opcache.jit_buffer_size 0
printf '\n--- contenu final ---\n'
cat "$FILE" )

Le garde set -eu arrête le script à la première erreur. Il est enfermé dans un sous-shell ( … ) : sans cette parenthèse, set -eu resterait actif dans votre session WHM et la moindre erreur de frappe ensuite la fermerait. Le test d’existence évite de créer accidentellement un fichier au mauvais endroit. La dernière commande affiche le fichier ENTIER, pas seulement les valeurs modifiées, pour confirmer que opcache.save_comments=1 et opcache.revalidate_freq=2 ont bien survécu.

La sortie doit contenir SEPT directives. Si opcache.save_comments=1 a disparu, restaurez la sauvegarde immédiatement : Laravel lit les docblocks et les attributs, son absence casse des paquets.

Variante de repli : édition manuelle avec nano 
nano /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini

Cette commande ouvre le fichier dans nano. Remplacez son contenu par le bloc final ci-dessous, enregistrez avec Ctrl+O puis Entrée, et quittez avec Ctrl+X.

opcache.memory_consumption=3584
opcache.max_accelerated_files=130987
opcache.interned_strings_buffer=640
opcache.revalidate_freq=2
opcache.save_comments=1
opcache.jit=disable

Voici le contenu final attendu, les sept directives. opcache.save_comments=1 et opcache.revalidate_freq=2 sont déjà présents dans le fichier actuel et doivent être conservés : save_comments est indispensable à Laravel, qui lit les docblocks et les attributs. Les omettre casserait des paquets. N’ajoutez pas validate_timestamps : sa valeur par défaut est déjà 1.

Dimensionnement mesuré le 2026-08-01 depuis une requête web réelle (SAPI fpm-fcgi, pas la ligne de commande) : 19 120 scripts occupaient 732,49 Mo, dont 365,54 Mo de bytecode, 128,00 Mo de chaînes internées et 238,95 Mo de structures internes. Le coût réel est donc de 31,6 Ko par script hors chaînes internées, et le ratio est de 1,70 clé par script.

Le plafond de 130 987 clés autorise environ 77 050 scripts. Le budget se répartit ainsi : 3 584 − 640 = 2 944 Mo pour le bytecode, soit une capacité d’environ 95 400 scripts. La table de clés sature donc bien avant la mémoire, avec 24 pour cent de marge — et c’est voulu : le mur que l’on doit atteindre en premier est celui des clés, pas celui de la mémoire.

Correction importante par rapport à la version précédente de cette procédure : le tampon de chaînes internées est alloué à l’intérieur de memory_consumption, pas en plus (vérifié dans /proc/self/smaps : un seul mapping partagé de 1 024 Mo, aucun second mapping de 128 Mo). Il faut donc lui faire une place explicite dans le segment, et non l’ajouter par-dessus. La mémoire partagée totale devient 3 584 Mo, soit 2,8 pour cent de la RAM du serveur — et non 3 328 Mo comme annoncé précédemment.

Pourquoi 640 Mo de chaînes internées et non 256 : le tampon actuel est saturé à 100 pour cent (807 913 chaînes, 0,00 Mo libre) avec seulement 19 120 scripts. Le ratio de 6,86 Ko par script qu’on en déduit est donc un plancher, pas la demande réelle : PHP a cessé d’y ajouter des chaînes une fois plein. Deux extrapolations indépendantes donnent 516 Mo (par le volume) et 541 Mo (par le nombre de chaînes) à 77 000 scripts — et ce sont elles aussi des planchers. 512 Mo serait déjà au taquet le jour de la mise en service; 640 Mo laisse environ 20 pour cent au-dessus du plancher estimé. Quand ce tampon déborde, PHP ne s’arrête pas : il alloue les chaînes dans la mémoire privée de chaque worker, la consommation RAM grimpe alors sans qu’aucun compteur d’OPcache ne le signale.

La vraie valeur ne sera connue qu’après ce redémarrage. C’est seulement quand le tampon aura de la place qu’il révélera sa demande réelle. Relever interned_strings_usage une fois le cache regarni permettra d’ajuster 640 Mo à la hausse ou à la baisse sur une mesure, plus sur une extrapolation.

La marge actuelle est inférieure à une application : chaque site Laravel du parc consomme entre 1 200 et 2 400 scripts, et il ne reste qu’environ 1 250 scripts de marge.

Ne touchez pas à opcache.validate_timestamps=1 ni à opcache.revalidate_freq=2. Avec un déploiement par rsync non atomique, validate_timestamps=1 est le seul filet contre du code à moitié copié.

3

Point de non-retour : tester avant tout redémarrage

( set -o pipefail
OUT=$(PHP_INI_SCAN_DIR=/opt/cpanel/ea-php84/root/etc/php.d /opt/cpanel/ea-php84/root/usr/bin/php -c /opt/cpanel/ea-php84/root/etc/php.ini -r 'exit(0);' 2>&1)
STATUS=$?
printf 'code de sortie = %s\n' "$STATUS"
printf 'sortie de PHP  = [%s]\n' "$OUT"
if [ "$STATUS" -eq 0 ] && ! printf '%s' "$OUT" | grep -Eiq '(warning|error|failed|syntax)'; then
  echo 'VERDICT : OK - la configuration est valide'
else
  echo 'VERDICT : ECHEC - NE PAS REDEMARRER, restaurer la sauvegarde'
fi )</dev/null

Cette commande force PHP 8.4 à charger le php.ini et tout le répertoire php.d, donc le fichier modifié, puis à sortir immédiatement. Elle ne touche à rien : OPcache ne s’initialise même pas en ligne de commande, enable_cli valant 0. Comme à l’étape 2, set -o pipefail est enfermé dans un sous-shell ( … ) pour qu’il ne reste pas actif dans votre session. Le verdict est affiché en clair plutôt que laissé à un silence à interpréter.

Attendu : code de sortie = 0, sortie de PHP = [] (vide), et VERDICT : OK.

Si cette étape renvoie la moindre erreur, NE PAS redémarrer. Allez directement au rollback de l’étape 6.

4

Redémarrer PHP-FPM

Il faut un RESTART, pas un reload. La mémoire partagée d’OPcache ne se redimensionne pas à chaud.

/scripts/restartsrv_apache_php_fpm --restart

Cette commande cPanel redémarre les maîtres PHP-FPM. Elle coupe brièvement les sites concernés et recrée leur mémoire partagée avec les nouvelles dimensions.

Variante directe pour PHP 8.4 :

systemctl restart ea-php84-php-fpm

Cette variante systemd redémarre uniquement le service PHP-FPM de ea-php84. Utilisez-la si la commande cPanel n’est pas disponible.

5

Vérifier côté web

Le CLI et PHP-FPM sont deux SAPI distincts avec deux caches différents. Un php -i en ligne de commande ne prouve rien sur le web.

La vérification côté web sera faite par l’équipe technique avec une sonde HTTP dédiée. Deux signaux confirment le succès : les valeurs actives lues côté web doivent être 3 584, 130 987, 640, disable et 0; le robot de surveillance externe Robotalp de tvhr9, identifiant 91534366, doit repasser au vert de lui-même.

Si Robotalp reste rouge, c’est le signal que les valeurs n’ont pas été appliquées au bon endroit.

6

Rollback en une commande

Il y a deux rollbacks différents. Choisissez selon que l’étape 4 a été exécutée ou non.

Cas A — AVANT le redémarrage (étape 4 pas encore faite)

C’est la situation actuelle. Aucun site n’a été affecté, il suffit de remettre le fichier en place. Ne redémarrez rien : ce serait justement appliquer les valeurs que vous cherchez à annuler.

cp /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini.backup-20260801-152210 /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini && cat /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini

Restaure la sauvegarde du 2026-08-01 à 15h22 et réaffiche le fichier pour confirmer le retour aux anciennes valeurs (1024, 128, 20000, tracing, 128M). Zéro coupure, zéro impact.

Cas B — APRÈS le redémarrage (étape 4 déjà faite)

FILE=/opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini; BACKUP=$(ls -1t "${FILE}".backup-* 2>/dev/null | head -n 1); [ -n "$BACKUP" ] && cp "$BACKUP" "$FILE" && /scripts/restartsrv_apache_php_fpm --restart

Choisit la sauvegarde horodatée la plus récente, la restaure au bon emplacement, puis redémarre PHP-FPM pour rétablir les anciennes valeurs. Cette variante-là coupe brièvement les sites, puisqu’il faut un second redémarrage pour défaire le premier.

Maintenance après une mise à jour serveur

Une mise à jour cPanel peut régénérer 10-opcache.ini. Le fichier 11-opcache-memora.ini persiste et garde la priorité, mais les valeurs actives côté web doivent être revérifiées après chaque mise à jour serveur avec la sonde HTTP de l’équipe.

grep -H -E '^[[:space:]]*;?[[:space:]]*opcache\.(memory_consumption|max_accelerated_files|interned_strings_buffer|jit|jit_buffer_size|validate_timestamps|revalidate_freq)[[:space:]]*=' /opt/cpanel/ea-php84/root/etc/php.d/10-opcache.ini /opt/cpanel/ea-php84/root/etc/php.d/11-opcache-memora.ini

Cette vérification rapide et sans modification affiche les valeurs sur disque ainsi que leur fichier d’origine. Elle confirme que le fichier 11- contient toujours les surcharges attendues; la sonde HTTP confirme ensuite les valeurs réellement actives dans FPM.

+

Activer le slowlog PHP-FPM

Le slowlog capture la pile PHP complète de toute requête dépassant 800 ms. En français simple, il montre exactement où PHP passe son temps lorsqu’une page ralentit. C’est l’outil de diagnostic le plus puissant et sans risque : il observe sans modifier le traitement de l’application. Il exige lui aussi un redémarrage.

Ajoutez ces directives dans la configuration du pool PHP-FPM du domaine à diagnostiquer, en adaptant le chemin du journal au domaine :

request_slowlog_timeout = 800ms
slowlog = /var/log/php-fpm/laveille.ai-slow.log

La première directive fixe le seuil de capture à 800 ms. La seconde indique où écrire les piles PHP; le dossier doit exister et être accessible au service.

/scripts/restartsrv_apache_php_fpm --restart

Cette commande applique la configuration du pool par un redémarrage. Elle entraîne la même brève interruption que l’étape 4.
